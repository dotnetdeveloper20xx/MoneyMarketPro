1.1 PLATFORM DESCRIPTION
--------------------------------------------------------------------------------

MoneyMarket is an enterprise-grade peer-to-peer (P2P) lending platform that
connects borrowers seeking capital with lenders looking for investment
opportunities. The platform operates as a two-sided digital marketplace,
facilitating the entire loan lifecycle from application through repayment
or resolution.

The platform serves as an intermediary that:
- Aggregates loan demand from verified borrowers
- Provides investment opportunities to qualified lenders
- Manages risk assessment and credit underwriting
- Enforces regulatory compliance and audit requirements
- Automates repayment collection and distribution

1.3 BUSINESS VALUE & MONETISATION MODEL
--------------------------------------------------------------------------------

REVENUE STREAMS:

1. Origination Fees (Borrower-side)
   - Percentage of loan amount (typically 1-5%)
   - Charged upon successful loan disbursement
   - Covers underwriting, platform, and servicing costs

2. Service Fees (Lender-side)
   - Percentage of interest earned (typically 10-15%)
   - Deducted from interest payments
   - Covers portfolio management and collection services

3. Late Payment Fees
   - Fixed or percentage-based penalties
   - Shared between platform and lender
   - Incentivizes timely repayment

4. Premium Services
   - Enhanced analytics for lenders
   - Priority listing for borrowers
   - Dedicated support tiers

5. Secondary Market (Future)
   - Transaction fees on loan part sales
   - Liquidity provision services

VALUE PROPOSITION:

For Borrowers:
- Access to capital outside traditional banking
- Competitive interest rates based on risk profile
- Streamlined digital application process
- Flexible loan terms

For Lenders:
- Higher yields compared to traditional fixed income
- Portfolio diversification across multiple loans
- Transparent risk metrics and borrower data
- Automated investment and reinvestment options

For the Platform:
- Scalable transaction-based revenue
- Network effects (more borrowers attract more lenders)
- Data moat from credit performance history
- Regulatory compliance as competitive barrier

1.4 WHY THIS ARCHITECTURE FOR FINTECH
--------------------------------------------------------------------------------

ARCHITECTURAL DECISION: Clean Architecture + CQRS + DDD

The chosen architecture addresses specific fintech requirements:

+-----------------------------------------------------------------------------+
|  REQUIREMENT              |  ARCHITECTURAL SOLUTION                         |
+-----------------------------------------------------------------------------+
|  Regulatory Compliance    |  Domain Events + Immutable Audit Logs          |
|                           |  Every state change is captured and traceable  |
+-----------------------------------------------------------------------------+
|  Complex Business Rules   |  DDD Aggregates + Domain Services              |
|                           |  Business logic encapsulated in domain layer   |
+-----------------------------------------------------------------------------+
|  High Read/Write Ratio    |  CQRS Pattern                                  |
|                           |  Optimized read models for dashboards          |
|                           |  Separate write models for transactions        |
+-----------------------------------------------------------------------------+
|  Audit Requirements       |  Event-Driven Architecture                     |
|                           |  Complete history of all domain events         |
+-----------------------------------------------------------------------------+
|  Security                 |  Clean Architecture Boundaries                 |
|                           |  Clear separation prevents data leakage        |
+-----------------------------------------------------------------------------+
|  Testability              |  Dependency Inversion                          |
|                           |  Domain logic testable without infrastructure  |
+-----------------------------------------------------------------------------+
|  Scalability              |  Modular Bounded Contexts                      |
|                           |  Can extract to microservices when needed      |
+-----------------------------------------------------------------------------+
|  Maintainability          |  Single Responsibility                         |
|                           |  Changes isolated to specific layers/contexts  |
+-----------------------------------------------------------------------------+

WHY NOT MICROSERVICES FROM DAY ONE?

Decision: Start with Modular Monolith, prepare for Microservices extraction.

Rationale:
1. Reduced operational complexity during initial development
2. Faster iteration and deployment cycles
3. Easier debugging and tracing across bounded contexts
4. Lower infrastructure costs
5. Bounded contexts can be extracted to services when scale demands

The architecture is designed with clear boundaries between contexts, making
future extraction straightforward without requiring a complete rewrite.

WHY CQRS FOR A LENDING PLATFORM?

The lending domain exhibits characteristics that make CQRS highly suitable:

1. Read-Heavy Operations:
   - Dashboard queries (borrower status, lender portfolio)
   - Marketplace browsing (hundreds of concurrent reads)
   - Reporting and analytics
   - Read-to-write ratio typically 10:1 or higher

2. Complex Write Operations:
   - Loan state transitions involve multiple invariants
   - Payment processing requires consistency guarantees
   - Risk calculations must be atomic

3. Different Data Shapes:
   - Write model: Normalized, aggregate-focused
   - Read model: Denormalized, view-specific

4. Audit Requirements:
   - Every command represents a user/system action
   - Natural fit for event logging and replay

WHY DDD FOR FINANCIAL DOMAINS?

Domain-Driven Design principles align with fintech requirements:

1. Ubiquitous Language:
   - "Loan", "Disbursement", "Arrears" mean the same thing to developers,
     business stakeholders, and regulators
   - Reduces translation errors between business and code

2. Aggregate Boundaries:
   - Loan aggregate enforces invariants (cannot overpay, cannot fund
     beyond requested amount)
   - Transaction boundaries align with business transaction boundaries

3. Domain Events:
   - LoanApproved, PaymentReceived, LoanDefaulted
   - Natural audit trail
   - Integration points for notifications, analytics, reporting

4. Value Objects:
   - Money, InterestRate, LoanTerm
   - Encapsulate validation and behavior
   - Prevent primitive obsession anti-pattern

1.5 KEY SYSTEM QUALITIES
--------------------------------------------------------------------------------

RELIABILITY:
- 99.9% uptime target for core transaction processing
- Graceful degradation for non-critical features
- Automatic retry with exponential backoff for transient failures
- Circuit breaker patterns for external service calls

SECURITY:
- Defense in depth (network, application, data layers)
- Encryption at rest (AES-256) and in transit (TLS 1.3)
- Role-based access control with principle of least privilege
- PII data masking in logs and non-production environments

COMPLIANCE:
- GDPR: Right to erasure, data portability, consent management
- Financial regulations: KYC/AML verification, transaction limits
- Audit: Immutable logs, tamper-evident records, retention policies

PERFORMANCE:
- API response time: < 200ms (p95) for read operations
- API response time: < 500ms (p95) for write operations
- Dashboard load time: < 2 seconds
- Support for 10,000 concurrent users

SCALABILITY:
- Horizontal scaling via Azure App Service
- Database read replicas for query distribution
- Caching layer for frequently accessed data
- Async processing for non-time-critical operations

CONTEXT RELATIONSHIPS:

1. IDENTITY & ACCESS (Generic Subdomain)
   - Relationship: Provides user identity to all other contexts
   - Pattern: Open Host Service (OHS) with Published Language (PL)
   - Integration: JWT tokens carry user claims consumed by other contexts

2. LENDING (Core Domain)
   - Relationship: Central context, orchestrates loan lifecycle
   - Pattern: Aggregate Root pattern for Loan entity
   - This is the competitive advantage - complex business rules live here

3. BORROWER MANAGEMENT (Supporting Subdomain)
   - Relationship: Upstream to Lending context
   - Pattern: Customer-Supplier
   - Provides borrower profiles and creditworthiness data

4. LENDER MANAGEMENT (Supporting Subdomain)
   - Relationship: Upstream to Lending context
   - Pattern: Customer-Supplier
   - Provides lender wallet balances and investment preferences

5. RISK & UNDERWRITING (Core Domain)
   - Relationship: Partner with Lending context
   - Pattern: Partnership (shared success criteria)
   - Risk models inform loan approval and pricing

6. PAYMENTS & TRANSACTIONS (Supporting Subdomain)
   - Relationship: Downstream from Lending
   - Pattern: Conformist (adapts to Lending's decisions)
   - Executes payment orders generated by Lending context

7. NOTIFICATION & MESSAGING (Generic Subdomain)
   - Relationship: Downstream from all contexts
   - Pattern: Open Host Service
   - Reacts to domain events, sends appropriate notifications

8. SUPPORT & DISPUTES (Supporting Subdomain)
   - Relationship: Autonomous with callbacks to Lending
   - Pattern: Separate Ways (mostly independent)
   - Handles customer service, can trigger loan restructuring

2.4 DOMAIN INVARIANTS
--------------------------------------------------------------------------------

Invariants are business rules that must ALWAYS be true. They are enforced
by aggregates and cannot be violated regardless of the operation.

LOAN AGGREGATE INVARIANTS:

1. Funding Limit
   Rule: TotalFundedAmount <= RequestedAmount
   Enforcement: Loan.AddFunding() method checks before adding
   Violation: Throws LoanOverfundedException

2. State Machine Transitions
   Rule: Only valid transitions allowed (see Section 4)
   Enforcement: Loan.TransitionTo() validates against allowed transitions
   Violation: Throws InvalidLoanStateTransitionException

3. Repayment Bounds
   Rule: SingleRepayment <= OutstandingBalance
   Enforcement: Loan.RecordPayment() validates amount
   Violation: Throws OverpaymentException

4. Immutable After Funding
   Rule: InterestRate, LoanTerm cannot change after PendingFunding state
   Enforcement: Property setters check current state
   Violation: Throws LoanTermsLockedException

5. Minimum Funding Threshold
   Rule: Loan cannot activate unless FundedAmount >= MinimumFundingPercentage
   Enforcement: Checked in TransitionTo(Active)
   Violation: Throws InsufficientFundingException

BORROWER PROFILE INVARIANTS:

1. Identity Verification
   Rule: Cannot apply for loan unless KYC status = Verified
   Enforcement: Application service checks before creating LoanApplication
   Violation: Throws BorrowerNotVerifiedException

2. Single Active Application
   Rule: Borrower can have only one application in Draft/Submitted/UnderReview
   Enforcement: Domain service checks existing applications
   Violation: Throws DuplicateApplicationException

3. Income Documentation
   Rule: Must have at least one verified income source
   Enforcement: BorrowerProfile.CanApplyForLoan() method
   Violation: Returns false, UI prevents application

LENDER PROFILE INVARIANTS:

1. Wallet Balance
   Rule: InvestmentAmount <= AvailableWalletBalance
   Enforcement: LenderProfile.CommitFunding() reserves amount
   Violation: Throws InsufficientFundsException

2. Accreditation Requirements
   Rule: High-risk investments require accredited investor status
   Enforcement: Checked when committing to Grade D+ loans
   Violation: Throws AccreditationRequiredException

3. Investment Limits
   Rule: SingleInvestment >= MinimumInvestmentAmount (platform rule)
   Enforcement: LenderProfile.CommitFunding() validates
   Violation: Throws MinimumInvestmentException

2.5 WHY LOAN IS A FIRST-CLASS AGGREGATE
--------------------------------------------------------------------------------

The Loan entity is the central aggregate of the platform for these reasons:

1. BUSINESS CENTRALITY
   - Every revenue stream flows through loans
   - All user journeys culminate in loan transactions
   - Loan performance metrics drive platform valuation

2. COMPLEX LIFECYCLE
   - Multiple states (7+ distinct states)
   - State transitions trigger numerous side effects
   - Long-lived (months to years)
   - Rich interaction history

3. CONSISTENCY BOUNDARY
   - Funding from multiple lenders must be atomic
   - Repayment allocation across funders must be consistent
   - State transitions affect multiple related entities

4. RICH INVARIANTS
   - Business rules are numerous and complex
   - Financial accuracy is critical
   - Regulatory requirements mandate strict enforcement

5. EVENT RICHNESS
   - Every transition emits domain events
   - Events drive notifications, analytics, compliance
   - Audit trail is comprehensive

2.8 REPAYMENT SCHEDULE MODEL
--------------------------------------------------------------------------------

Repayments follow an amortization schedule generated at loan disbursement.

SCHEDULE GENERATION:
- Generated when loan transitions to Active state
- Uses standard amortization formula
- Each installment specifies principal and interest portions
- Schedule is immutable once generated (restructuring creates new schedule)

AMORTIZATION FORMULA:
M = P * [r(1+r)^n] / [(1+r)^n - 1]

Where:
- M = Monthly payment
- P = Principal (loan amount)
- r = Monthly interest rate (annual rate / 12)
- n = Number of payments (loan term in months)

REPAYMENT SCHEDULE ENTITY:

+-----------------------------------------------------------------------------+
|  REPAYMENT SCHEDULE DETAILS                                                 |
+-----------------------------------------------------------------------------+
|                                                                             |
|  Fields:                                                                    |
|  - SequenceNumber: int (1, 2, 3... n)                                       |
|  - DueDate: DateTime                                                        |
|  - PrincipalPortion: Money                                                  |
|  - InterestPortion: Money                                                   |
|  - TotalDue: Money                                                          |
|  - OutstandingBalanceAfter: Money                                           |
|  - Status: RepaymentStatus (Scheduled/Paid/Partial/Overdue/Waived)          |
|  - PaidAmount: Money                                                        |
|  - PaidAt: DateTime?                                                        |
|  - DaysOverdue: int (calculated)                                            |
|                                                                             |
|  Example 36-month loan of $10,000 at 12% APR:                               |
|  +------+------------+------------+----------+----------+----------+        |
|  | #    | Due Date   | Principal  | Interest | Total    | Balance  |        |
|  +------+------------+------------+----------+----------+----------+        |
|  | 1    | 2026-02-01 | $232.14    | $100.00  | $332.14  | $9,767.86|        |
|  | 2    | 2026-03-01 | $234.46    | $97.68   | $332.14  | $9,533.40|        |

|  | ...  | ...        | ...        | ...      | ...      | ...      |        |
|  | 36   | 2029-01-01 | $328.86    | $3.28    | $332.14  | $0.00    |        |
|  +------+------------+------------+----------+----------+----------+        |

2.10 AUDIT & COMPLIANCE CONSIDERATIONS
--------------------------------------------------------------------------------

DOMAIN-LEVEL AUDIT:

Every aggregate maintains audit information:

1. CREATION AUDIT
   - CreatedAt: DateTime (UTC)
   - CreatedBy: UserId

2. MODIFICATION AUDIT
   - UpdatedAt: DateTime (UTC)
   - UpdatedBy: UserId

3. STATE TRANSITION AUDIT (Loan Aggregate)
   - Full history of state changes
   - Who triggered, when, why
   - Immutable log within aggregate

4. DOMAIN EVENTS
   - Every significant action emits an event
   - Events are persisted for audit trail
   - Events can reconstruct state history

COMPLIANCE-DRIVEN DESIGN DECISIONS:

+-----------------------------------------------------------------------------+
|  REQUIREMENT          |  DESIGN DECISION                                    |
+-----------------------------------------------------------------------------+
|  Data Retention       |  Soft deletes with IsDeleted flag                   |
|                       |  Separate archive tables after retention period     |
+-----------------------------------------------------------------------------+
|  Right to Erasure     |  PII marked separately from transactional data      |
|  (GDPR Art. 17)       |  Anonymization procedure for completed loans        |
+-----------------------------------------------------------------------------+
|  Audit Trail          |  LoanStateTransition entity within aggregate        |
|                       |  Domain events persisted to EventLog table          |
+-----------------------------------------------------------------------------+
|  Data Integrity       |  Aggregate invariants prevent invalid states        |
|                       |  Database constraints as safety net                 |
+-----------------------------------------------------------------------------+
|  Access Logging       |  All data access logged via middleware              |
|                       |  Sensitive field access triggers alerts             |
+-----------------------------------------------------------------------------+
|  Transaction Limits   |  Domain service enforces regulatory limits          |
|                       |  Configurable per jurisdiction                      |
+-----------------------------------------------------------------------------+

3.10 ROLE-BASED ACCESS CONTROL IMPLEMENTATION
--------------------------------------------------------------------------------

The RBAC system is implemented using ASP.NET Core Identity with custom claims.

CLAIM STRUCTURE:
- Claims follow format: {resource}:{action} or {resource}:{action}:{scope}
- Scope can be "own" (own resources only) or "all" (all resources)

POLICY EXAMPLES:

```
Policy: "CanApproveLoan"
Requirements:
  - Claim "crm:application:approve" OR
  - Claim "admin:loan:approve-all"

Policy: "CanViewBorrowerProfile"
Requirements:
  - (Claim "borrower:profile:read" AND User.Id == Profile.UserId) OR
  - Claim "crm:borrower:read" OR
  - Claim "support:user:read" OR
  - Claim "admin:*"

Policy: "CanInvest"
Requirements:
  - Claim "lender:loan:invest"
  - User.LenderProfile.AccreditationStatus == "Verified" (for high-risk loans)
  - User.LenderProfile.Wallet.AvailableBalance >= InvestmentAmount
```

ROLE-TO-CLAIMS MAPPING:

+-----------------------------------------------------------------------------+
| Role    | Claims                                                            |
+-----------------------------------------------------------------------------+
| Borrower| borrower:profile:*, borrower:kyc:upload, borrower:loan:*,         |
|         | borrower:repayment:make, support:ticket:create,                   |
|         | support:ticket:read:own                                           |
+-----------------------------------------------------------------------------+
| Lender  | lender:profile:*, lender:wallet:*, lender:marketplace:browse,     |
|         | lender:loan:invest, lender:portfolio:read, support:ticket:*:own   |
+-----------------------------------------------------------------------------+
| CRM     | crm:application:*, crm:borrower:read, crm:kyc:verify, crm:risk:*, |
|         | admin:escalate                                                    |
+-----------------------------------------------------------------------------+
| Support | support:ticket:*, support:user:read, support:loan:read,           |
|         | support:message:send                                              |
+-----------------------------------------------------------------------------+
| Admin   | admin:* (wildcard - all administrative permissions)               |
+-----------------------------------------------------------------------------+

4.1 STATE MACHINE OVERVIEW
--------------------------------------------------------------------------------

The Loan entity follows a strict state machine pattern that enforces valid
transitions and emits domain events at each state change. This ensures
business rule compliance and provides a complete audit trail.

DESIGN PRINCIPLES:
1. All state changes go through the aggregate root (Loan.TransitionTo)
2. Invalid transitions throw exceptions
3. Every transition emits a domain event
4. Transitions are recorded in LoanStateTransition entity
5. External systems cannot directly modify loan status

4.2 STATE DEFINITIONS
--------------------------------------------------------------------------------

+---------------+--------------------------------------------------------------+
| State         | Description                                                  |
+---------------+--------------------------------------------------------------+

| Submitted     | Application submitted for review. No further edits allowed. |

+---------------+--------------------------------------------------------------+
| UnderReview   | Risk assessment complete. Awaiting CRM/Admin review.        |

+---------------+--------------------------------------------------------------+
| InfoRequested | Additional information requested from borrower.             |
|               | Clock paused on review timeline.                            |
+---------------+--------------------------------------------------------------+
| Approved      | Application approved. Ready for marketplace listing.        |
|               | Loan entity created from application.                       |
+---------------+--------------------------------------------------------------+
| Rejected      | Application rejected. Terminal state for application.       |
|               | Reason stored. Borrower notified.                           |
+---------------+--------------------------------------------------------------+
| PendingFunding| Loan listed on marketplace. Awaiting lender investments.    |
|               | Funding deadline applies.                                   |
+---------------+--------------------------------------------------------------+
| FullyFunded   | Loan fully funded. Awaiting disbursement.                   |
|               | Lender funds reserved.                                      |
+---------------+--------------------------------------------------------------+
| Active        | Loan disbursed. Repayment schedule in effect.               |
|               | Payments being collected.                                   |
+---------------+--------------------------------------------------------------+
| InArrears     | One or more payments overdue > 7 days.                      |
|               | Collections process initiated.                              |
+---------------+--------------------------------------------------------------+
| Restructured  | Loan terms modified due to hardship.                        |
|               | New schedule generated. Transitions back to Active.         |
+---------------+--------------------------------------------------------------+
| Defaulted     | Loan deemed unrecoverable. 90+ days overdue.                |

+---------------+--------------------------------------------------------------+
| WrittenOff    | Defaulted loan written off from books.                      |

+---------------+--------------------------------------------------------------+
| Completed     | All payments received. Loan closed successfully.            |

4.5 BUSINESS RULES ENFORCING TRANSITIONS
--------------------------------------------------------------------------------

Each transition is guarded by business rules validated within the aggregate:

RULE: Submit Application
+-----------------------------------------------------------------------------+
| Preconditions:                                                              |
| - Application status is Draft                                               |
| - All required fields are populated                                         |
| - Borrower KYC status is Verified                                           |
| - No other active application exists for borrower                           |
| - Requested amount within platform limits                                   |
+-----------------------------------------------------------------------------+

RULE: Approve Loan
+-----------------------------------------------------------------------------+
| Preconditions:                                                              |
| - Application status is UnderReview                                         |
| - Risk assessment is completed                                              |
| - Approver has sufficient authority (amount within limits)                  |
| - No fraud flags present (or overridden with justification)                 |
| Postconditions:                                                             |
| - Loan entity created with approved terms                                   |
| - Interest rate locked                                                      |
+-----------------------------------------------------------------------------+

RULE: Add Funding
+-----------------------------------------------------------------------------+
| Preconditions:                                                              |
| - Loan status is PendingFunding                                             |
| - Funding deadline not expired                                              |
| - Investment amount >= minimum investment                                   |
| - Lender wallet has sufficient available balance                            |
| - Total funding after investment <= requested amount                        |
| - Lender is accredited (if loan is high-risk grade)                         |
| Postconditions:                                                             |
| - LoanFunding record created                                                |
| - Lender wallet funds reserved                                              |
| - If fully funded, transition to FullyFunded                                |
+-----------------------------------------------------------------------------+

RULE: Disburse Loan
+-----------------------------------------------------------------------------+
| Preconditions:                                                              |
| - Loan status is FullyFunded                                                |
| - All lender funds are reserved                                             |
| - Borrower bank account verified                                            |
| Postconditions:                                                             |
| - Lender reserved funds debited                                             |
| - Origination fee deducted                                                  |
| - Net amount transferred to borrower                                        |
| - Repayment schedule generated                                              |
| - Loan status set to Active                                                 |
+-----------------------------------------------------------------------------+

RULE: Record Payment
+-----------------------------------------------------------------------------+
| Preconditions:                                                              |
| - Loan status is Active or InArrears                                        |
| - Payment amount > 0                                                        |
| - Payment amount <= outstanding balance                                     |
| - Payment reference is unique (idempotency)                                 |
| Postconditions:                                                             |
| - Payment allocated to principal and interest                               |
| - Repayment schedule updated                                                |
| - Lender wallets credited proportionally                                    |
| - If all payments complete, transition to Completed                         |
| - If overdue cleared, transition from InArrears to Active                   |
+-----------------------------------------------------------------------------+

RULE: Transition to InArrears
+-----------------------------------------------------------------------------+
| Preconditions:                                                              |
| - Loan status is Active                                                     |
| - At least one repayment is overdue > 7 days                                |
| Postconditions:                                                             |
| - Arrears notifications sent                                                |
| - Collections process initiated                                             |
| - Lenders notified of arrears status                                        |
+-----------------------------------------------------------------------------+

RULE: Restructure Loan
+-----------------------------------------------------------------------------+
| Preconditions:                                                              |
| - Loan status is InArrears                                                  |
| - Restructuring proposal submitted                                          |
| - Admin approval obtained                                                   |
| - New terms are viable (borrower can reasonably pay)                        |
| Postconditions:                                                             |
| - Old schedule marked as superseded                                         |
| - New repayment schedule generated                                          |
| - Loan status set to Restructured then Active                               |
| - All parties notified                                                      |
+-----------------------------------------------------------------------------+

RULE: Default Loan
+-----------------------------------------------------------------------------+
| Preconditions:                                                              |
| - Loan status is InArrears                                                  |
| - Days overdue >= 90 (configurable)                                         |
| - Collections attempts exhausted                                            |
| - Admin confirms default                                                    |
| Postconditions:                                                             |
| - Loss calculated and distributed to lenders                                |
| - Lender portfolio metrics updated                                          |
| - Borrower credit impact recorded                                           |
| - Regulatory reporting triggered                                            |
+-----------------------------------------------------------------------------+

4.6 STATE MACHINE IMPLEMENTATION
--------------------------------------------------------------------------------

The state machine is implemented within the Loan aggregate using the
State pattern with explicit transition validation.

IMPLEMENTATION APPROACH:

```
public class Loan : AggregateRoot<LoanId>
{
    private static readonly Dictionary<LoanStatus, LoanStatus[]> AllowedTransitions =
        new()
        {
            { LoanStatus.Draft, new[] { LoanStatus.Submitted, LoanStatus.Cancelled } },
            { LoanStatus.Submitted, new[] { LoanStatus.UnderReview, LoanStatus.Rejected } },
            { LoanStatus.UnderReview, new[] { LoanStatus.Approved, LoanStatus.Rejected,
                                               LoanStatus.InfoRequested } },
            { LoanStatus.InfoRequested, new[] { LoanStatus.UnderReview,
                                                 LoanStatus.Cancelled } },
            { LoanStatus.Approved, new[] { LoanStatus.PendingFunding } },
            { LoanStatus.PendingFunding, new[] { LoanStatus.FullyFunded,
                                                  LoanStatus.Cancelled } },
            { LoanStatus.FullyFunded, new[] { LoanStatus.Active } },
            { LoanStatus.Active, new[] { LoanStatus.Completed, LoanStatus.InArrears } },
            { LoanStatus.InArrears, new[] { LoanStatus.Active, LoanStatus.Restructured,
                                             LoanStatus.Defaulted } },
            { LoanStatus.Restructured, new[] { LoanStatus.Active } },
            { LoanStatus.Defaulted, new[] { LoanStatus.WrittenOff, LoanStatus.Completed } },
            // Terminal states have no allowed transitions
            { LoanStatus.WrittenOff, Array.Empty<LoanStatus>() },
            { LoanStatus.Completed, Array.Empty<LoanStatus>() },
            { LoanStatus.Cancelled, Array.Empty<LoanStatus>() },
            { LoanStatus.Rejected, Array.Empty<LoanStatus>() }
        };

    public void TransitionTo(LoanStatus newStatus, UserId transitionedBy, string reason)
    {
        if (!CanTransitionTo(newStatus))
        {
            throw new InvalidLoanStateTransitionException(Status, newStatus);
        }

        var previousStatus = Status;
        Status = newStatus;
        UpdatedAt = DateTime.UtcNow;

        // Record transition for audit
        var transition = new LoanStateTransition(
            Id,
            previousStatus,
            newStatus,
            DateTime.UtcNow,
            transitionedBy,
            reason
        );
        _stateTransitions.Add(transition);

        // Emit appropriate domain event
        RaiseDomainEvent(CreateTransitionEvent(previousStatus, newStatus));
    }

    public bool CanTransitionTo(LoanStatus newStatus)
    {
        return AllowedTransitions.TryGetValue(Status, out var allowed)
               && allowed.Contains(newStatus);
    }
}
```

5.1 WHY CQRS FOR MONEYMARKET
--------------------------------------------------------------------------------

CQRS (Command Query Responsibility Segregation) separates read and write
operations into distinct models. This architectural pattern is particularly
suited for MoneyMarket due to:

1. ASYMMETRIC READ/WRITE RATIO
   - Reads far outnumber writes (estimated 20:1)
   - Dashboard queries: thousands per minute
   - Marketplace browsing: high-frequency reads
   - Loan applications: relatively infrequent writes

2. DIFFERENT OPTIMIZATION NEEDS
   - Writes: Consistency, validation, domain rules
   - Reads: Performance, denormalization, aggregation

3. COMPLEX DOMAIN OPERATIONS
   - Loan approval involves multiple aggregates
   - Payment distribution touches many entities
   - Risk calculations require complex business logic

4. VARIED QUERY PATTERNS
   - Borrower dashboard: own loans, payments, status
   - Lender portfolio: investments across many loans
   - Admin reports: aggregate statistics, trends
   - CRM queue: filtered, sorted, paginated lists

5. AUDIT REQUIREMENTS
   - Commands represent user intent
   - Natural audit trail via command logging
   - Event sourcing compatibility for future

CQRS CONCEPTUAL MODEL:

+-----------------------------------------------------------------------------+
|                              CQRS ARCHITECTURE                              |
+-----------------------------------------------------------------------------+
|                                                                             |
|  CLIENT (Angular App)                                                       |

5.2 COMMAND RESPONSIBILITY
--------------------------------------------------------------------------------

Commands represent user intent to change system state. They are:
- Named in imperative form (ApplyForLoan, ApproveLoan)
- Validated before processing
- Handled by exactly one handler
- May emit domain events
- Return minimal data (usually just success/failure + ID)

COMMAND DESIGN PRINCIPLES:

1. IMMUTABILITY
   - Commands are immutable records
   - Cannot be modified after creation

2. SELF-CONTAINED
   - All data needed for processing is included
   - No need to fetch additional context
   - Reduces coupling to other services

3. EXPLICIT INTENT
   - Name clearly states the action
   - Not "UpdateLoan" but "ApproveLoan", "RejectLoan"
   - Each command has single responsibility

4. VALIDATION-READY
   - Structure supports FluentValidation
   - Required fields are non-nullable
   - Domain constraints expressed as attributes

5.4 QUERY RESPONSIBILITY
--------------------------------------------------------------------------------

Queries represent requests for data without side effects. They are:
- Named as questions or data requests (GetBorrowerDashboard)
- Return DTOs optimized for the use case
- May use denormalized read models
- Can be cached for performance
- Never modify state

QUERY STRUCTURE:

+-----------------------------------------------------------------------------+
|  QUERY ANATOMY                                                              |
+-----------------------------------------------------------------------------+
|                                                                             |
|  public record GetBorrowerDashboardQuery : IQuery<BorrowerDashboardDto>     |
|  {                                                                          |
|      // WHO: Identification                                                 |
|      public BorrowerProfileId BorrowerId { get; init; }                     |
|                                                                             |
|      // WHAT: Optional filters/parameters                                   |
|      public DateRange? DateFilter { get; init; }                            |
|      public bool IncludeCompletedLoans { get; init; } = false;              |
|  }                                                                          |
|                                                                             |
+-----------------------------------------------------------------------------+

QUERY DESIGN PRINCIPLES:

1. USE-CASE SPECIFIC
   - One query per UI view/component
   - Returns exactly what the view needs
   - Avoids over-fetching or under-fetching

2. DENORMALIZED RESULTS
   - DTOs are flat when possible
   - Pre-calculated aggregates
   - Ready for display without transformation

3. CACHEABLE
   - Results can be cached by query key
   - Cache invalidation via domain events
   - TTL-based expiration for stale data

4. PERFORMANT
   - Direct database queries (not through aggregates)
   - Optimized indexes on read tables
   - Pagination for large result sets

5.6 COMMAND AND QUERY HANDLERS
--------------------------------------------------------------------------------

Handlers contain the logic to process commands and queries. They are
registered with MediatR and follow a consistent pattern.

COMMAND HANDLER EXAMPLE: ApplyForLoanCommandHandler
+-----------------------------------------------------------------------------+
| public class ApplyForLoanCommandHandler                                     |
|     : ICommandHandler<ApplyForLoanCommand, LoanApplicationId>               |
| {                                                                           |
|     private readonly IBorrowerProfileRepository _borrowerRepo;              |
|     private readonly ILoanApplicationRepository _applicationRepo;           |
|     private readonly IUnitOfWork _unitOfWork;                               |
|     private readonly IDateTimeProvider _dateTimeProvider;                   |
|                                                                             |
|     public async Task<Result<LoanApplicationId>> Handle(                    |
|         ApplyForLoanCommand command,                                        |
|         CancellationToken cancellationToken)                                |
|     {                                                                       |
|         // 1. Load aggregate                                                |
|         var borrower = await _borrowerRepo.GetByIdAsync(                    |
|             command.BorrowerId, cancellationToken);                         |
|                                                                             |
|         if (borrower is null)                                               |
|             return Result.Failure<LoanApplicationId>(                       |
|                 DomainErrors.Borrower.NotFound);                            |
|                                                                             |
|         // 2. Check preconditions                                           |
|         if (!borrower.CanApplyForLoan())                                    |
|             return Result.Failure<LoanApplicationId>(                       |
|                 DomainErrors.Borrower.NotEligibleForLoan);                  |
|                                                                             |
|         // 3. Check for existing active application                         |
|         var hasActive = await _applicationRepo                              |
|             .HasActiveApplicationAsync(command.BorrowerId, cancellationToken);|
|         if (hasActive)                                                      |
|             return Result.Failure<LoanApplicationId>(                       |
|                 DomainErrors.LoanApplication.DuplicateActive);              |
|                                                                             |
|         // 4. Create aggregate                                              |
|         var application = LoanApplication.Create(                           |
|             LoanApplicationId.Create(),                                     |
|             command.BorrowerId,                                             |
|             Money.Create(command.RequestedAmount, command.Currency),        |
|             LoanTerm.FromMonths(command.TermInMonths),                      |
|             command.Purpose,                                                |
|             command.PurposeDescription,                                     |
|             _dateTimeProvider.UtcNow                                        |
|         );                                                                  |
|                                                                             |
|         // 5. Persist                                                       |
|         _applicationRepo.Add(application);                                  |
|         await _unitOfWork.SaveChangesAsync(cancellationToken);              |
|                                                                             |
|         // 6. Return result (domain events dispatched by SaveChanges)       |
|         return Result.Success(application.Id);                              |
|     }                                                                       |
| }                                                                           |

|                 l.InterestRate,                                             |
|                 l.TermInMonths,                                             |
|                 l.DisbursedAt                                               |
|             FROM Loans l                                                    |
|             WHERE l.BorrowerId = @BorrowerId                                |
|               AND l.Status IN ('Active', 'InArrears');                      |
|                                                                             |
|             SELECT TOP 5                                                    |
|                 rs.LoanId,                                                  |
|                 rs.DueDate,                                                 |
|                 rs.TotalAmount,                                             |
|                 rs.Status                                                   |
|             FROM RepaymentSchedules rs                                      |
|             INNER JOIN Loans l ON rs.LoanId = l.Id                          |
|             WHERE l.BorrowerId = @BorrowerId                                |
|               AND rs.Status = 'Scheduled'                                   |
|               AND rs.DueDate >= GETUTCDATE()                                |
|             ORDER BY rs.DueDate;                                            |
|         ";                                                                  |
|                                                                             |
|         using var multi = await _connection.QueryMultipleAsync(             |
|             sql, new { query.BorrowerId });                                 |
|                                                                             |
|         var profile = await multi.ReadSingleOrDefaultAsync<ProfileDto>();   |
|         var loans = (await multi.ReadAsync<LoanSummaryDto>()).ToList();     |
|         var payments = (await multi.ReadAsync<PaymentDto>()).ToList();      |
|                                                                             |
|         var result = MapToDashboardDto(profile, loans, payments);           |
|                                                                             |
|         // Cache for 5 minutes                                              |
|         await _cache.SetAsync(cacheKey, result, TimeSpan.FromMinutes(5));   |
|                                                                             |
|         return result;                                                      |
|     }                                                                       |
| }                                                                           |

5.7 PIPELINE BEHAVIOURS
--------------------------------------------------------------------------------

MediatR pipeline behaviours provide cross-cutting concerns that apply to
all commands and queries. They form a chain of responsibility.

PIPELINE ORDER:

+-----------------------------------------------------------------------------+
|                         MEDIATR PIPELINE                                    |
+-----------------------------------------------------------------------------+
|                                                                             |
|  Request -->                                                                |
|                                                                             |
|  1. LoggingBehaviour                                                        |
|     |  - Log request start with correlation ID                              |
|     |  - Log request end with duration                                      |
|     |  - Log exceptions                                                     |
|     v                                                                       |
|  2. ValidationBehaviour                                                     |
|     |  - Run FluentValidation validators                                    |
|     |  - Return validation errors if any                                    |
|     |  - Short-circuit pipeline on failure                                  |
|     v                                                                       |
|  3. AuthorizationBehaviour                                                  |
|     |  - Check user permissions                                             |
|     |  - Verify resource ownership                                          |
|     |  - Return 403 if unauthorized                                         |
|     v                                                                       |
|  4. AuditBehaviour (Commands only)                                          |
|     |  - Log command to audit table                                         |
|     |  - Capture user, timestamp, payload                                   |
|     v                                                                       |
|  5. TransactionBehaviour (Commands only)                                    |
|     |  - Begin database transaction                                         |
|     |  - Commit on success                                                  |
|     |  - Rollback on exception                                              |
|     v                                                                       |
|  6. PerformanceBehaviour                                                    |
|     |  - Track execution time                                               |
|     |  - Log slow requests (> 500ms)                                        |
|     |  - Emit metrics                                                       |
|     v                                                                       |
|  7. CachingBehaviour (Queries only)                                         |
|     |  - Check cache for result                                             |
|     |  - Return cached if valid                                             |
|     |  - Cache result after handler                                         |
|     v                                                                       |
|  HANDLER                                                                    |
|     |                                                                       |
|     v                                                                       |
|  <-- Response                                                               |
|                                                                             |
+-----------------------------------------------------------------------------+

BEHAVIOUR IMPLEMENTATION EXAMPLES:

ValidationBehaviour:
+-----------------------------------------------------------------------------+
| public class ValidationBehaviour<TRequest, TResponse>                       |
|     : IPipelineBehavior<TRequest, TResponse>                                |
|     where TRequest : IRequest<TResponse>                                    |
| {                                                                           |
|     private readonly IEnumerable<IValidator<TRequest>> _validators;         |
|                                                                             |
|     public async Task<TResponse> Handle(                                    |
|         TRequest request,                                                   |
|         RequestHandlerDelegate<TResponse> next,                             |
|         CancellationToken cancellationToken)                                |
|     {                                                                       |
|         if (!_validators.Any())                                             |
|             return await next();                                            |
|                                                                             |
|         var context = new ValidationContext<TRequest>(request);             |
|         var validationResults = await Task.WhenAll(                         |
|             _validators.Select(v => v.ValidateAsync(context, cancellationToken)));|
|                                                                             |
|         var failures = validationResults                                    |
|             .SelectMany(r => r.Errors)                                      |
|             .Where(f => f is not null)                                      |
|             .ToList();                                                      |
|                                                                             |
|         if (failures.Count > 0)                                             |
|             throw new ValidationException(failures);                        |
|                                                                             |
|         return await next();                                                |
|     }                                                                       |
| }                                                                           |

AuditBehaviour:
+-----------------------------------------------------------------------------+
| public class AuditBehaviour<TRequest, TResponse>                            |
|     : IPipelineBehavior<TRequest, TResponse>                                |
|     where TRequest : ICommand<TResponse>                                    |
| {                                                                           |
|     private readonly IAuditLogRepository _auditLog;                         |
|     private readonly ICurrentUserService _currentUser;                      |
|     private readonly IDateTimeProvider _dateTime;                           |
|                                                                             |
|     public async Task<TResponse> Handle(                                    |
|         TRequest request,                                                   |
|         RequestHandlerDelegate<TResponse> next,                             |
|         CancellationToken cancellationToken)                                |
|     {                                                                       |
|         var commandName = typeof(TRequest).Name;                            |
|         var userId = _currentUser.UserId;                                   |
|         var payload = JsonSerializer.Serialize(request);                    |
|                                                                             |
|         var auditEntry = new AuditLogEntry                                  |
|         {                                                                   |
|             CommandName = commandName,                                      |
|             UserId = userId,                                                |
|             Payload = payload,                                              |
|             Timestamp = _dateTime.UtcNow,                                   |
|             CorrelationId = Activity.Current?.Id                            |
|         };                                                                  |
|                                                                             |
|         try                                                                 |
|         {                                                                   |
|             var response = await next();                                    |
|             auditEntry.Success = true;                                      |

|         }                                                                   |
|         catch (Exception ex)                                                |

|         }                                                                   |

|         {                                                                   |

|         }                                                                   |
|     }                                                                       |
| }                                                                           |

5.8 IDEMPOTENCY
--------------------------------------------------------------------------------

Financial operations require idempotency to prevent duplicate processing.

IDEMPOTENCY STRATEGY:

1. IDEMPOTENCY KEY
   - Client generates unique key per operation
   - Key is GUID or hash of operation + timestamp
   - Stored with operation result

2. CHECK BEFORE PROCESSING
   - Query for existing key before handling command
   - Return cached result if found
   - Prevents duplicate charges/payments

3. STORAGE
   - Idempotency records stored in dedicated table
   - Include: Key, CommandType, Result, CreatedAt, ExpiresAt
   - TTL-based cleanup (e.g., 24 hours)

IDEMPOTENCY IMPLEMENTATION:

+-----------------------------------------------------------------------------+
| public class IdempotencyBehaviour<TRequest, TResponse>                      |
|     : IPipelineBehavior<TRequest, TResponse>                                |
|     where TRequest : IIdempotentCommand<TResponse>                          |
| {                                                                           |
|     private readonly IIdempotencyStore _store;                              |
|                                                                             |
|     public async Task<TResponse> Handle(                                    |
|         TRequest request,                                                   |
|         RequestHandlerDelegate<TResponse> next,                             |
|         CancellationToken cancellationToken)                                |
|     {                                                                       |
|         var key = request.IdempotencyKey;                                   |
|                                                                             |
|         // Check for existing result                                        |
|         var existing = await _store.GetAsync<TResponse>(key, cancellationToken);|
|         if (existing is not null)                                           |
|         {                                                                   |
|             // Return cached result (duplicate request)                     |
|             return existing;                                                |
|         }                                                                   |
|                                                                             |
|         // Process command                                                  |
|         var response = await next();                                        |
|                                                                             |
|         // Store result for future duplicate requests                       |
|         await _store.SetAsync(                                              |
|             key,                                                            |
|             response,                                                       |
|             TimeSpan.FromHours(24),                                         |
|             cancellationToken);                                             |
|                                                                             |
|         return response;                                                    |
|     }                                                                       |
| }                                                                           |

6.9 WHY DOMAIN HAS ZERO DEPENDENCIES
--------------------------------------------------------------------------------

The Domain project is the core of the application and MUST have zero
external dependencies (except .NET BCL). This ensures:

1. TESTABILITY
   - Domain logic can be unit tested without mocking infrastructure
   - Tests run fast (no database, no external services)
   - True isolation of business rules

2. FRAMEWORK INDEPENDENCE
   - Can change ORM without touching domain
   - Can switch from SQL Server to PostgreSQL
   - Can change from Azure to AWS

3. LONGEVITY
   - Domain outlives frameworks
   - Business rules don't change when upgrading .NET version
   - Core logic remains stable

4. CLARITY
   - Pure business logic, no technical concerns
   - Easy to understand by domain experts
   - Matches ubiquitous language

WHAT BELONGS IN DOMAIN:

+ Aggregate roots and entities
+ Value objects
+ Domain events
+ Domain exceptions
+ Repository interfaces (contracts only)
+ Domain service interfaces (contracts only)
+ Enums and constants
+ Business rule validations (invariants)

WHAT DOES NOT BELONG IN DOMAIN:

- Database annotations ([Table], [Column])
- EF Core references
- External service implementations
- Logging
- Serialization attributes
- DTOs (belong in Application)
- Validation attributes (use FluentValidation in Application)

UNIT OF WORK:
+-----------------------------------------------------------------------------+
| // MoneyMarket.Persistence/Repositories/UnitOfWork.cs                       |
|                                                                             |
| public class UnitOfWork : IUnitOfWork                                       |
| {                                                                           |
|     private readonly MoneyMarketDbContext _context;                         |
|     private readonly IDomainEventDispatcher _eventDispatcher;               |
|                                                                             |
|     public async Task<int> SaveChangesAsync(CancellationToken ct = default) |
|     {                                                                       |
|         // Dispatch domain events before save                               |
|         await DispatchDomainEventsAsync();                                  |
|                                                                             |
|         // Persist changes                                                  |
|         return await _context.SaveChangesAsync(ct);                         |
|     }                                                                       |
|                                                                             |
|     private async Task DispatchDomainEventsAsync()                          |
|     {                                                                       |
|         var entities = _context.ChangeTracker                               |
|             .Entries<IHasDomainEvents>()                                    |
|             .Where(e => e.Entity.DomainEvents.Any())                        |
|             .Select(e => e.Entity)                                          |
|             .ToList();                                                      |
|                                                                             |
|         var domainEvents = entities                                         |
|             .SelectMany(e => e.DomainEvents)                                |
|             .ToList();                                                      |
|                                                                             |
|         entities.ForEach(e => e.ClearDomainEvents());                       |
|                                                                             |
|         foreach (var domainEvent in domainEvents)                           |
|         {                                                                   |
|             await _eventDispatcher.DispatchAsync(domainEvent);              |
|         }                                                                   |
|     }                                                                       |
| }                                                                           |

7.1 DATABASE STRATEGY
--------------------------------------------------------------------------------

PRIMARY DATABASE: SQL Server (Azure SQL Database in production)
DEVELOPMENT DATABASE: SQL Server LocalDB or EF Core In-Memory
ORM: Entity Framework Core 8.x
QUERY OPTIMIZATION: Dapper for complex read queries

STRATEGY RATIONALE:

1. SQL Server chosen for:
   - ACID compliance critical for financial transactions
   - Strong Azure integration
   - Advanced features (temporal tables, JSON support, row-level security)

2. EF Core for writes because:
   - Change tracking for aggregates
   - Migration management
   - Interceptors for auditing and events

3. Dapper for reads because:
   - Raw SQL performance for complex queries
   - Ideal for denormalized read models

15.1 AGGREGATE ROOT: LOAN

public class Loan : AggregateRoot<LoanId>
{
    // Identity
    public LoanId Id { get; private set; }
    public LoanApplicationId ApplicationId { get; private set; }
    public BorrowerProfileId BorrowerId { get; private set; }

    // Core Properties
    public Money Amount { get; private set; }
    public InterestRate InterestRate { get; private set; }
    public LoanTerm Term { get; private set; }
    public LoanPurpose Purpose { get; private set; }
    public RiskGrade RiskGrade { get; private set; }
    public LoanStatus Status { get; private set; }

    // Timestamps
    public DateTime? ListedAt { get; private set; }
    public DateTime? FundedAt { get; private set; }
    public DateTime? DisbursedAt { get; private set; }
    public DateTime? CompletedAt { get; private set; }
    public DateTime FundingDeadline { get; private set; }

    // Collections (owned entities)
    private readonly List<LoanFunding> _fundings = new();
    public IReadOnlyCollection<LoanFunding> Fundings => _fundings.AsReadOnly();

    private readonly List<RepaymentSchedule> _repaymentSchedules = new();
    public IReadOnlyCollection<RepaymentSchedule> RepaymentSchedules
        => _repaymentSchedules.AsReadOnly();

    private readonly List<LoanStateTransition> _stateTransitions = new();
    public IReadOnlyCollection<LoanStateTransition> StateTransitions
        => _stateTransitions.AsReadOnly();

    // Calculated Properties
    public Money FundedAmount => Money.FromSum(_fundings.Select(f => f.Amount));
    public Money OutstandingBalance => CalculateOutstanding();
    public bool IsFullyFunded => FundedAmount >= Amount;

    // Factory Method
    public static Loan Create(
        LoanId id, LoanApplicationId appId, BorrowerProfileId borrowerId,
        Money amount, InterestRate rate, LoanTerm term,
        LoanPurpose purpose, RiskGrade grade, DateTime fundingDeadline)
    {
        var loan = new Loan
        {
            Id = id,
            ApplicationId = appId,
            BorrowerId = borrowerId,
            Amount = amount,
            InterestRate = rate,
            Term = term,
            Purpose = purpose,
            RiskGrade = grade,
            Status = LoanStatus.PendingFunding,
            FundingDeadline = fundingDeadline,
            ListedAt = DateTime.UtcNow
        };

        loan.RaiseDomainEvent(new LoanListedEvent(id, amount, rate));
        return loan;
    }

    // Behaviors
    public Result AddFunding(LenderProfileId lenderId, Money amount)
    {
        if (Status != LoanStatus.PendingFunding)
            return Result.Failure(DomainErrors.Loan.NotPendingFunding);

        if (FundedAmount + amount > Amount)
            return Result.Failure(DomainErrors.Loan.OverFunded);

        var funding = LoanFunding.Create(Id, lenderId, amount);
        _fundings.Add(funding);

        RaiseDomainEvent(new LoanPartiallyFundedEvent(Id, lenderId, amount));

        if (IsFullyFunded)
            TransitionTo(LoanStatus.FullyFunded, null, "Fully funded");

        return Result.Success();
    }

    public Result TransitionTo(LoanStatus newStatus, UserId? by, string reason)
    {
        if (!CanTransitionTo(newStatus))
            return Result.Failure(DomainErrors.Loan.InvalidTransition);

        var transition = new LoanStateTransition(Id, Status, newStatus, by, reason);
        _stateTransitions.Add(transition);

        Status = newStatus;
        RaiseDomainEvent(CreateTransitionEvent(newStatus));

        return Result.Success();
    }
}

15.2 VALUE OBJECT: MONEY

public class Money : ValueObject
{
    public decimal Value { get; }
    public Currency Currency { get; }

    private Money(decimal value, Currency currency)
    {
        if (value < 0)
            throw new ArgumentException("Money cannot be negative");
        Value = value;
        Currency = currency;
    }

    public static Money Create(decimal value, string currencyCode)
        => new(value, Currency.FromCode(currencyCode));

    public static Money Zero(Currency currency) => new(0, currency);

    public Money Add(Money other)
    {
        EnsureSameCurrency(other);
        return new Money(Value + other.Value, Currency);
    }

    public Money Subtract(Money other)
    {
        EnsureSameCurrency(other);
        return new Money(Value - other.Value, Currency);
    }

    public static Money operator +(Money a, Money b) => a.Add(b);
    public static Money operator -(Money a, Money b) => a.Subtract(b);
    public static bool operator >(Money a, Money b) => a.Value > b.Value;
    public static bool operator <(Money a, Money b) => a.Value < b.Value;
    public static bool operator >=(Money a, Money b) => a.Value >= b.Value;
    public static bool operator <=(Money a, Money b) => a.Value <= b.Value;

    protected override IEnumerable<object> GetEqualityComponents()
    {
        yield return Value;
        yield return Currency;
    }
}

15.3 VALUE OBJECT: RISK GRADE
--------------------------------------------------------------------------------

public class RiskGrade : ValueObject
{
    public char Grade { get; }      // A, B, C, D, E, F
    public int Subgrade { get; }    // 1-5 (1 is best)

    private static readonly Dictionary<char, (decimal minRate, decimal maxRate)> RateBands = new()
    {
        ['A'] = (0.06m, 0.10m),
        ['B'] = (0.10m, 0.13m),
        ['C'] = (0.13m, 0.17m),
        ['D'] = (0.17m, 0.22m),
        ['E'] = (0.22m, 0.28m),
        ['F'] = (0.28m, 0.35m)
    };

    private RiskGrade(char grade, int subgrade)
    {
        if (!char.IsUpper(grade) || grade < 'A' || grade > 'F')
            throw new ArgumentException("Grade must be A-F");
        if (subgrade < 1 || subgrade > 5)
            throw new ArgumentException("Subgrade must be 1-5");

        Grade = grade;
        Subgrade = subgrade;
    }

    public static RiskGrade Create(char grade, int subgrade) => new(grade, subgrade);
    public static RiskGrade Parse(string value) =>
        new(value[0], int.Parse(value[1].ToString()));

    public bool IsAccreditedOnly => Grade >= 'E';

    public decimal GetMinInterestRate() => RateBands[Grade].minRate;
    public decimal GetMaxInterestRate() => RateBands[Grade].maxRate;

    public override string ToString() => $"{Grade}{Subgrade}";

    protected override IEnumerable<object> GetEqualityComponents()
    {
        yield return Grade;
        yield return Subgrade;
    }
}
